## Decisions (current-code adaptations of the investigation)

- D1. Detection stays inside `assertSiteAvailable` (one `executeScript`, no extra round trip). `captchaGuard` calls it at its top (run.ts ~183), in the provider load loop (~214) and in the CAPTCHA `driver.wait` (~251), and every `waitWithCaptcha` iteration calls `captchaGuard`. That already covers the phase-2 paths: `waitFor`, `waitEarly`, `settle`, `segment()`, `runFill`, `waitForSection` (early branch) and `waitForPostback`. No new polling is needed there.
- D2. The detector script must NOT contain the substrings `document.readyState`, `const challengePage` or `const captchaSubmit`. `captcha.test.ts` `fixture()` routes scripts by those substrings and returns its `busy` boolean for everything else, so `true` must still mean busy. Also keep the script free of `executeAsyncScript` and extra calls so readyState call counts in existing tests do not change.
- D3. The real gaps are the places that decide "the form reloaded" without going through the guard. These are the `unexpectedReload()` call sites, which set `context.risk = true` via the `persistence: possible` event. They are in `fastFillSection`: `waitFor` post-check (~1259), `runFill` (~1291, ~1295), `recheck` (~1336), `segment()` (~1363, ~1367), `settle` (~1422), plus the `settle` TimeoutError conversion (~1427). Change `unexpectedReload` to take the driver and run a denied-page check first. A denied redirect before any POST must leave `risk === false`.
- D4. Denied-page check helper for those paths is separate from the throwing guard. It must tolerate a navigation in flight: `isAccessDenied(driver)` runs the same pathname test, catches `isNavigationError` and returns false. `unexpectedReload(driver)` calls it, throws `AccessDeniedError` if true, and otherwise keeps today's behavior unchanged. The navigation-error catch sites go through the same helper because they call `unexpectedReload`.
- D5. Recovery orchestration lives in `workflow/run.ts` (it needs the private `navigate`, `emit`, `execution`, `waitForSection`, `checkpoint`). The pure pieces (constants, error class, pathname matcher, backoff helper) live in `workflow/site-busy.ts` so tests can import them without a browser. Constants go in `site-busy.ts`, not `fast-fill.ts`, to avoid a new dependency from the detector on the fast-fill module.
- D6. Events: reuse `{ type: "phase", phase: "recovery", message }`. Note that `ExecutionController.event` writes `phase` and `message` into the job. After a successful recovery, emit `{ type: "phase", phase: "section", message }` to restore the section phase. No change to `lib/execution-state.ts` or `lib/execution-controller.ts`. Existing event enumeration tests stay valid.
- D7. Budget is per run, as a closure variable inside `executeWorkingHoliday` (not module state, so tests and concurrent runs are isolated). It is shared by the pre-wizard path and the section loop. The session re-auth one-shot (`recoveredSession`) stays a separate per-section budget.
- D8. Kill switch `NZWH_ACCESS_DENIED_RECOVERY=0` is read once per run, next to `fastEntrySnapshot()` in `executeWorkingHoliday`. Disabled means detect, log and stop immediately with the fixed message. Detection itself is never disabled.
- D9. Read-only verify uses `planSection(name, data)` (exported from `fast-fill.ts`) filtered to `entry.applicable`, plus `readFieldValues(driver, ids)` and compares each value to `entry.expected`. Lookups are skipped, as `planSection` already does. Occupation is not automated, so the occupation-widget policy is untouched. A null or different value means unverified. This is conservative: it never triggers a refill or SAVE.

## Risks to watch while implementing

- Fixture routing in `captcha.test.ts`: the detector script text must not contain `document.readyState`, `const challengePage` or `const captchaSubmit` (D2).
- `captchaGuard`'s provider load loop calls `assertSiteAvailable` before `captchaPending`; a denied page must throw there too (already true, since the call is shared). The `finally` emits `captcha waiting:false`.
- Catch-binding rename in item 3 must keep every existing branch's behavior byte-for-byte; run `fast-fill-run.test.ts` after the edit.
- `ExecutionController.checkpoint()` returns early while a section is running, so stop inside recovery arrives only via `signal.aborted` (hence the abortable backoff and `checkCancelled()`).
- Do not follow the page's "close all browser windows" advice; attach mode (`handles[0]`) reuses the same tab.
